# ADR 0001: Интеграция Catalog → Booking через Outbox + событийную шину, а не синхронный REST

- Статус: Принято
- Дата: 2026-09-14

## Контекст

Booking Service должен знать состав мест (`Seat`) для события, чтобы резервировать их при старте продаж. Это самый нагруженный момент всей системы (flash-sale) — именно ради него выбран данный домен.

Рассматривались два варианта:

1. **Синхронный REST-вызов** Booking → `GET /api/events/{id}/seats` в Catalog в момент резервирования (или для прогрева кэша прямо перед стартом продаж).
2. **Событийная интеграция**: Catalog публикует интеграционное событие о составе мест при публикации события, Booking строит и хранит собственную копию данных, необходимую для резервирования.

### Проблемы варианта 1

- Catalog становится точкой отказа и bottleneck ровно в момент пиковой нагрузки — то есть там, где по цели проекта должна демонстрироваться устойчивость системы, а не наоборот.
- Два сервиса вынуждены согласовывать одно и то же состояние (`Seat.Status`) синхронно под конкурентным доступом — это разрушает границу Bounded Context и провоцирует распределённые блокировки поперёк сервисов.
- Недоступность Catalog делает Booking недоступным, хотя домены логически независимы (Catalog — read-heavy справочник, Booking — write-heavy резервирование).

## Решение

Catalog и Booking интегрируются асинхронно через шину сообщений (RabbitMQ), а атомарность "изменение данных + публикация события" в Catalog обеспечивается паттерном **Transactional Outbox**:

1. При публикации события (`PublishEventHandler`) Catalog в **той же транзакции БД**, где создаются `Seat`, записывает в таблицу `outbox_messages` интеграционное событие `EventPublished` (снимок мест: `SeatId`, `SectionId`, `Row`, `Number`, `Price`, `Category`).
2. Фоновый воркер (`OutboxDispatcherService`) вычитывает необработанные записи из `outbox_messages` и публикует их в RabbitMQ через `IPublishEndpoint` (MassTransit используется только как клиент шины на этом этапе, без встроенного outbox-транспорта MassTransit — чтобы сознательно реализовать и понять паттерн руками, а не спрятать его в библиотеке).
3. Booking Service подписывается на `EventPublished` и строит **собственную** таблицу мест с полями, нужными именно для резервирования (лок, TTL, версия для optimistic concurrency). Данные не запрашиваются синхронно у Catalog.
4. `Seat.Status` в Catalog остаётся read-моделью для UI/каталога и в перспективе будет обновляться асинхронно через события из Booking (`SeatReserved`, `SeatReleased`, `SeatSold`) — то есть данные текут в обе стороны, но всегда через шину, никогда синхронным запросом в момент пиковой нагрузки.

## Альтернативы, от которых отказались

- **Встроенный Outbox MassTransit** (`AddEntityFrameworkOutbox`) — годная production-практика, но на этапе обучения сознательно откладывается: сначала реализуем паттерн руками (таблица, фоновый диспетчер, at-least-once, идемпотентность на стороне потребителя), чтобы на собеседовании уметь объяснить механику, а не пересказать документацию библиотеки. Переход на встроенный outbox — возможное отдельное упражнение позже, с явным сравнением trade-off.
- **Синхронный REST с кэшированием на стороне Booking** — не решает проблему единой точки отказа в момент старта продаж и требует ручной инвалидации кэша, что сложнее, чем разовая подписка на событие.

## Последствия

- Появляется предсказуемая зависимость Catalog → RabbitMQ (в docker-compose нужен контейнер `rabbitmq`).
- Появляется paradigm eventual consistency между Catalog и Booking: после публикации события какое-то время (до обработки outbox) состав мест в Booking ещё не появится. Для UI это не критично (продажи ещё не стартовали к моменту публикации), но это первый практический пример eventual consistency в проекте — стоит явно проговорить на собеседовании.
- Нужен `MessageId` в `EventEnvelope`, совпадающий с `Id` записи в outbox, чтобы Booking мог реализовать Inbox/дедупликацию на своей стороне (at-least-once delivery от RabbitMQ + возможные повторные публикации из-за сбоя воркера).
- Добавляется новая инфраструктурная единица — фоновый `BackgroundService` в Catalog, требующая мониторинга (задержка обработки outbox, размер очереди необработанных сообщений) — хороший повод завести первую бизнес-метрику для Prometheus.
